# 付款範例需求與明確假設

本章延伸先前「結果未知轉交對帳」的教學案例，不是支付業界通用規則。

1. 時序圖從待付款開始，假設驗證與庫存預留成功。
2. 付款前取消可關單並釋放庫存；取得處理權後，送出一次扣款請求。
3. 每筆訂單最多一筆付款請求紀錄，使用固定 paymentKey。API 的冪等、重複請求拒絕等下層機制假設存在，但本章未實作。
4. 成功轉已付款；明確失敗關單並安排庫存釋放；未知保留庫存，不重新扣款。
5. 狀態寫入成功是本圖前提；資料庫寫入失敗、釋放補償另訂規格。
6. 只重試查詢原付款結果，最多三次；每次查詢成功回應或逾時皆計數。n 為本次查詢結束後累計次數。
7. 若查詢確認成功／失敗，就轉對應狀態；只有仍未知且 n < 3 才繼續；仍未知且 n = 3 則交人工。
8. 人工處理是本章邊界，保留庫存，不自動判定付款失敗。查詢間隔、最大等待時間、人工處理與庫存保留期限未定，不可直接部署。
9. 每次自動查詢保留一筆紀錄，包含查詢逾時；類別圖只描述自動查詢，人工歷程不包含於 0..3。
10. 回呼競態、重複回呼、退款、出貨與關閉後再付款不在模型內。重下單屬新訂單。

## 三圖對照

| 初次訊息結果 | 訂單轉移 | 後續 |
| --- | --- | --- |
| 明確成功 | Processing → Paid | 本圖停止展開 |
| 明確失敗 | Processing → Closed | 釋放補償另訂 |
| 等待逾時／未知 | Processing → Unknown | 有限次查詢 |

付款請求關聯基數 0..1、自動查詢 0..3 與上述假設一致。概念類別不等於資料表，不會自動強制基數。
