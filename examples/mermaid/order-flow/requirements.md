# 範例需求與邊界

這是教學用虛構規格，不是實際支付系統設計。箭頭表示處理流程，不代表資料流或模組依賴。

| ID | 需求 | 圖上對照 |
| --- | --- | --- |
| R1 | 提交後先驗證資料；不合法時拒絕本次提交 | submit → valid → rejected |
| R2 | 資料有效後嘗試原子性預留庫存；失敗則拒絕 | valid → reserve → unavailable |
| R3 | 預留成功才建立待付款訂單 | reserve → pending |
| R4 | 本圖只處理付款請求送出前的取消；取消須釋放庫存 | pending → cancel → cancelled |
| R5 | 未取消時送出付款請求 | cancel → pay |
| R6 | 已確認付款成功後，訂單轉為已付款 | result → confirmed |
| R7 | 已確認失敗後關閉本次訂單並釋放庫存；不自動重試 | result → failed |
| R8 | 逾時不等於失敗；結果未知時保留庫存，轉交對帳流程 | result → reconcile |

## 刻意簡化

- 本圖假設庫存預留與待付款訂單建立的協調已由下層實作保證；建單失敗補償不在此圖內。
- 不包含請求送出後的取消競態、重複回呼、支付冪等、退款、出貨與通知。
- 對帳是另一個流程。本圖到轉交即結束，不暗示可以永久保留庫存；保留期限、對帳重試及人工處理須另訂規格。
- 庫存不足與資料錯誤不在圖內繞回重試；修改後重新提交屬於新一次操作。
- 範例的成功、失敗與待確認均來自規格，不能由 AI 擅自增加退款或無限重試。
