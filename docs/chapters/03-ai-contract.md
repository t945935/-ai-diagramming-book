# 第 3 章：讓 AI 按規格畫圖

> 樣章草稿。提示詞可以約束工作範圍，不能代替實際驗證。

## 3.1 先給來源與邊界

「你是頂尖架構師」無法告訴 AI 哪條關係是真的。更有用的輸入是：讀者、用途、原始需求、節點清單、箭頭意思、例外、未知與交付格式。

本書 [通用提示詞](../../prompts/diagram-contract.md) 將這些欄位分開。沒有填寫的資訊應明確留白。不要讓 AI 把「可能有退款」解讀成「請自行設計完整退款流程」。

第一輪可以只要求它整理節點、關係和待確認問題。先比對文字清單，再產生圖，通常比看到一張漂亮但錯誤的圖後逐條拆解容易。

## 3.2 把禁止事項寫成可觀察行為

「不要幻覺」太抽象。對訂單案例，可改成：

- 不加入未提供的服務或退款分支。
- 付款逾時只能走待確認，不走明確失敗。
- 只畫付款送出前取消，不假設送出後取消一定安全。
- 不新增查詢次數、等待期限或人工責任人。
- 回報未執行的檢查，不生成假造的成功紀錄。

這些限制仍要靠驗收確認。[第 10 章](10-debugging.md) 的反向依賴案例展示了兩份資料都能成功產圖、但只有一份符合需求的情況。

## 3.3 用穩定 ID 分開內容和顯示

節點 ID 是引用，標籤是給讀者看的文字。將 `reconcile` 的標籤改短，不一定要重新命名節點；反過來，把 `payment` 全部取代也可能誤改不同層次的物件。

要求 AI 保留既有 ID、端點與群組，只修改批准範圍。若改變圖意，先更新需求或契約，再更新來源。不要因測試失敗就先把預期值改掉。

## 3.4 四層驗收不能互相替代

| 層次 | 要取得的證據 | 常見誤判 |
| --- | --- | --- |
| 語法／環境 | 實際命令、版本、退出碼及可讀產物 | JSON 合法就能在編輯器正常使用 |
| 語意 | 每條需求與節點、關係或情境的對照 | exit 0 就表示業務正確 |
| 視覺 | 最終圖片的中文、裁切、壓線與閱讀尺寸 | SVG 可解析就不會缺字 |
| 交付／可編輯性 | 原生來源、真實修改、保存及重開 | PNG 看得到就等於可編輯 |

[驗收紀錄模板](../../templates/diagram-acceptance.md) 預設所有項目都是「未測」，並要求每一項寫證據位置。沒有真實執行就保持未測，不必為了把表填滿而杜撰結果。

本書某些編輯器測試只驗證模型序列化或瀏覽器儲存重載，未測原生檔案保存對話框。這些結果有價值，但不能換名稱說成「所有另存與重開都通過」。

## 3.5 修圖時縮小變更範圍

若標籤太擠，可以要求：「保留三個結果分支與所有端點，縮短顯示文字，把完整條件移到圖例，重產預覽。」這讓修改有邊界，也有可判定的結果。

若出現 Parse error，先給完整錯誤與最小來源；若中文字缺字，先確認字型和產圖環境。不同故障需要不同證據，不要把所有問題都丟回一句「重畫」。

AI 輸出的 SVG、原生檔與說明也可能包含外部資源或文字指令。把檔案內容當作資料，不讓它要求你上傳憑證或執行不相關命令。公開前另查個資、內部網址、嵌入場景與授權。

## 3.6 一輪任務的完成條件

交付原始檔、預覽、需求對照與執行紀錄，並列出仍未確認的問題。如果要發布到 GitHub，還要確認檔案真的出現在指定提交，CI 的 head SHA 與該提交相同。

目前核心 CI 只驗證部分程式與契約；不能據此宣布全書所有圖通過。完整的版本、權限與發布邊界見 [第 12 章](12-automation-security.md)。

## 3.7 練習與參考修正

不良提示詞：「畫一張完整訂單圖，異常都自動解決，輸出 PNG，說明已測試。」

可改為：「依指定 R1–R8 需求產生 Mermaid 流程來源與預覽。只涵蓋付款送出前取消與初次付款結果；未知走對帳交接，不補期限。先列節點、關係與疑問，確認後再產圖。實際渲染並保存錯誤／退出碼，逐條對照需求；不能執行時寫未測。」

參考修正刪掉了沒有定義的『完整』與『自動解決』，保留原生來源，並把成功聲明改成需要證據的驗收工作。接著可用 [第 4 章 Mermaid](04-mermaid.md) 的檔案實作這輪流程。
