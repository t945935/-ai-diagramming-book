# 第 2 章：六套工具怎麼選

> 樣章草稿。本章說明本書採用的分工，不是完整功能排名或跨版本效能評測。

## 2.1 先看交付方式

如果圖要放在 Markdown 文件裡，並跟著文字一起審查，文字來源很方便。如果交接者要拖動方框、調整線條，原生圖形編輯器通常更適合。這兩個需求有時比圖有多少種形狀更重要。

選工具前先問：誰維護原始檔？在哪裡閱讀？需要精確表示什麼？是否需要人工拖曳？能否安裝渲染器？可接受哪些資訊在轉換時重建？

## 2.2 本書的六種分工

| 工具 | 本書用途 | 維護來源 | 選用時要接受的成本 |
| --- | --- | --- | --- |
| Mermaid | 文件內的步驟與分支 | .mmd | 顯示平台版本不同，需實際渲染；複雜圖可能需要拆分 |
| D2 | 服務、容器與邊界 | .d2 | 排版依引擎與字型；不保證跨引擎位置相同 |
| PlantUML | 時序、狀態與概念類別 | .puml | 精確圖意仍靠規格；工具不能替你決定未知結果 |
| Graphviz | 資料生成的依賴總覽與子圖 | 本例 JSON 加生成程式 | 必須定義邊方向；密集資料可能需要篩選視圖 |
| draw.io | 人工微調與圖形交接 | .drawio | 需保留模型端點，實際拖曳、保存及重開 |
| Excalidraw | 工作坊白板與未定問題 | .excalidraw | 手繪外觀不承載批准狀態，仍需決策紀錄 |

Graphviz 的原始來源也可以直接是 DOT；本書第 7 章選擇由 JSON 生成，所以生成 DOT 不是最上游。原始檔的地位由流程決定，不能只看副檔名。

## 2.3 相同主題可以有不同選擇

「付款」不是工具選型答案。如果要討論哪些問題還沒決定，用 Excalidraw；如果要核對 API、資料庫和支付服務的訊息次序，用 PlantUML；如果只是文件裡交代成功、失敗、未知三種出口，可以用 Mermaid。

[第 13 章](13-refund-project.md) 刻意把退款受理交給 Mermaid，把單筆退款紀錄的結果交給 PlantUML。兩張圖分工後，沒有必要再把同一流程重畫四次。

可用 [選型紀錄模板](../../templates/tool-selection.md) 留下主要需求、選擇理由和未採用方案。這比在團隊討論中只說「大家都用這套」更容易交接。

## 2.4 自動排版與人工排版的差別

文字來源便於比較差異，但一次標籤變長就可能改變整張圖的排列。人工座標可以細調，卻也可能在複製貼上後失去連線綁定。兩種方式都需要驗收。

若唯一要求是「看起來跟原 PNG 一樣」，應先追問是否需要編輯、語意或資料生成。視覺相似並不能保證原生模型保留，尤其不能拿匯入一張截圖當作可編輯重建。

跨工具時先列出要保留的契約。第 11 章只對齊 D2／draw.io 的四條呼叫端點，沒有聲稱所有標籤、樣式、座標相等。Graphviz 的付款模組也不能直接映射成外部支付服務。

## 2.5 選型練習

| 情境 | 本書建議 | 判定理由 |
| --- | --- | --- |
| README 中說明訂單結果 | Mermaid | 文件步驟與分支是主要交付 |
| 檢查平台內外服務歸屬 | D2 | 容器和邊界比操作時序重要 |
| 討論查詢逾時與回覆順序 | PlantUML | 需要參與者與訊息次序 |
| 從資料列出付款模組的潛在影響範圍 | Graphviz | 資料生成、依賴篩選與循環處理 |
| 非程式背景同事要拖動既有架構圖 | draw.io | 人工編輯與端點保留是需求 |
| 尚未決定對帳間隔與負責人 | Excalidraw | 保留未定事項，不先編造完整流程 |

這些是練習參考，不是排他規則。若團隊已經有可維護的工具鏈，提出替代選擇時應比較實際交付成本，而非只比工具清單。

下一章把選好的工具、需求與驗收方式放進同一份 AI 任務。
